# Генеральный план работ — Bannerlord Co-op

Версия 1 · 2026-10-18 · Bannerlord 1.4.8 · заменяет укрупнённо `MVP_ROADMAP.md` (тот остаётся как история).

## 0. Цель и рамки (ADR-0007)

Общая кампания до 4 игроков: каждый ходит по карте своей армией в реальном времени (скорость 1x
залочена). Когда кто-то начинает бой — кампания встаёт на паузу у всех, все игроки попадают в этот
бой: выбирают сторону (за инициатора / против), слот (лорд → офицер/компаньон → класс войск) или
наблюдение. Слоты бронируются хостом. PvP — в scope; осады — первый этап после MVP (ADR-0007). Персонажи игроков бессмертны
(нокаут → выбор нового слота, если есть, иначе наблюдатель). Хостинг: выделенный хост и
Steam-приглашение. Один бой одновременно.

## 1. Архитектура верхнего уровня (рабочая гипотеза)

```
            ┌──────────── Авторитетный хост кампании ────────────┐
            │  Campaign simulation (единственная истинная)        │
            │  SessionManager · PlayerRegistry · TimeControl(1x)  │
            │  BattleCoordinator (пауза, приглашение, слоты)      │
            └───────┬──────────────────────────┬──────────────────┘
       Transport (LiteNetLib: IP/dedicated │ Steam Networking: invite)
            ┌───────┴─────┐            ┌────────┴────┐
            │  Клиент 1..3 │  ...       │ Хост ведёт  │ (вариант A, ADR-0006 принят 2026-10-25:
            │  реплика мира│            │ бой сам      │  своя синхронизация миссии по ITransport)
            └──────────────┘            └─────────────┘
```

Модули кода: `Core` (чистый C#, тестируемый: сессии, слоты, брони, машины состояний, протокол) ·
`Networking` (транспорт, сериализация, два бэкенда) · `Campaign` (адаптеры кампании, Harmony) ·
`Battle` (адаптеры Mission/Agent) · `UI` (Gauntlet) · `Module` (точка входа SubModule).

Ключевые развилки, которые закрывает исследование (Phase 2):
- **G1-a**: бой через нативный MP-стек (вариант B) или своя синхронизация миссии (вариант A) — ADR-0006: **принят A** (2026-10-25, research 0011), B отклонён для MVP.
- **G1-b**: как клиент получает мир кампании (передача сейва при входе + поток изменений vs полная репликация).
- **G1-c**: выделенный хост кампании — отдельный экземпляр игры без игрока (headless?) или хост = один из игроков.

## 2. Фазы

Оценки — грубые, «календарь» при ~10–15 ч/нед вашего времени + Claude. «Окна» = 5-часовые окна
лимита Pro (ориентир, не гарантия). Каждая фаза закрывается `/mvp-check`.

### Phase 0 — Окружение и репозиторий · 1 нед · 1–2 окна
- Довести чек-лист `ENVIRONMENT_CHECKLIST.md` до зелёного.
- Локальная папка = git-репо; локальный Claude Code работает из неё.
- `docs/research/0001-environment.md`: версии SDK/IDE/сервера, пути логов, запуск 2 экземпляров игры
  на одном ПК (да/нет), версия Dedicated Server.
- **Готово, когда**: все пункты чек-листа ✅, 0001 записан.

### Phase 1 — Оболочка мода · 1–2 нед · 2–4 окна
- Проект из BUTR Module.Template (MIT), net472, ID модуля **не** «Coop» (напр. `BannerCoopTW`).
- SubModule.xml, зависимость от Bannerlord.Harmony, логгер в свой файл, конфиг, вывод версии в игре.
- Скрипт сборки/деплоя в `Modules` через junction `mb2` (без машинных путей в Git).
- GitHub Actions: сборка на CI против BUTR.ReferenceAssemblies 1.4.8 (без DLL игры).
- **Готово, когда**: мод виден в лаунчере, грузится без ошибок, пишет лог; CI зелёный.

### Phase 2 — Исследование API (декомпиляция) · 2–3 нед · 5–8 окон
Декомпиляция 1.4.8 в `_decompiled/` (вне Git). Отдельная заметка на каждую тему:
- 0002 Время кампании: тик, скорость, пауза, блокировка 1x.
- Позитивный контроль для варианта B (≤1 окно, параллельно Spike A1): штатный custom-сервер + клиент на этом ПК
  через обычное меню игры. Если штатная пара тоже не соединяется на loopback — проблема в окружении (брандмауэр/Npcap/один Steam-аккаунт), и S2 надо повторить (ADR-0006 «Reopen B», условие a).
- 0003 Начало боя: `PlayerEncounter`/`MapEvent`, стороны, участники, осады.
- 0004 Миссия: создание, спавн агентов, `Agent.Main`/контроллеры, смена управляемого агента, нокаут,
  подкрепления, отступление, завершение и результаты.
- 0005 Нативный MP: `GameNetwork`, `MissionPeer`, кастомный режим игры, загрузка модуля на Dedicated
  Server, спавн кампанийных персонажей/экипировки в MP, сцены кампании в MP.
- 0006 Сохранения: сериализация, можно ли передать сейв клиенту и загрузить.
- 0007 Steam: Steamworks.NET в поставке, лобби/инвайты/сокеты.
- 0008 Поток/тред-модель игры, где безопасно применять сетевые изменения.
- 0009 Внутренности мода Diplomacy: поведения, сохраняемые типы, действия UI.
- **Решения (Gate G1)** — приняты 2026-10-18: ADR-0006 (вариант B-listen, условно, гейты S1/S2; **пересмотрен 2026-10-25 → вариант A**, research 0011),
  ADR-0010 модель синхронизации кампании, ADR-0011 модель хостинга, ADR-0012 транспорт
  (номера сдвинуты: 0008 = Diplomacy, 0009 = ID модуля).
- **Готово, когда**: у каждой операции из списка — вердикт «есть API / нужен патч / невозможно».

### Phase 3 — Ядро (чистый C#) · 1–2 нед · 3–5 окон · можно параллельно с Phase 2
- `BattleSession`, `SlotCatalog` (лорды/офицеры/классы, PvP-стороны, осадные роли), `ReservationService`
  (атомарность, таймаут 10–15 с), машины состояний игрока и сущности, правило нокаута.
- Протокол сообщений (версионирование, рукопожатие, проверка версии мода/игры).
- Юнит-тесты на все кейсы из `BATTLE_PARTICIPATION.md` (одновременные заявки, последний лучник, …).
- **Готово, когда**: тесты зелёные на CI, покрытие ключевых кейсов 100%.

### Phase 4 — Сетевой стенд · 2–3 нед · 4–6 окон
- Абстракция транспорта (теперь несёт и боевой трафик: unreliable-sequenced для снимков, reliable для событий); бэкенд №1 LiteNetLib (IP/выделенный); фейковые клиенты-заглушки
  (идея из SkyCraft) — 4 клиента без запуска игры.
- Лобби: подключение, ready, отключение, переподключение-заглушка, пинг.
- Внутри игры: 2 экземпляра обмениваются сообщением и синхронизируют одну тестовую сущность.
- **Готово, когда**: 4 фейковых клиента проходят сценарий брони слотов через сеть; 2 игры видят друг друга.

### Phase 5 — Фундамент общей кампании · 2–4 мес · 25–45 окон (самая большая)
Подэтапы, каждый с демо:
- 5a Вход в игру: хост грузит кампанию; клиент получает мир (по решению G1-b), создаёт/получает героя и партию; **окно «Продолжение кампании»** при загрузке кооп-сейва (пауза до выбора героев, отсутствующие — бот; SESSION_RESUME.md); позднее подключение с созданием нового героя (до 4 мест,
  спайк S3, можно отключить в MVP).
- 5b Время: глобальные 1x, общая пауза/продолжение, синхронизация тика.
- 5c Движение партий игроков по карте (ввод клиента → хост → всем).
- 5d ИИ-партии и мир: хост симулирует, клиенты отображают (поведения ИИ на клиентах отключены).
- 5e Поселения и меню, торговля, инвентарь, найм, управление отрядом.
- 5f Диалоги, квесты, отношения; 5g королевства/кланы/дипломатия + **совместимость с модом Diplomacy** (ADR-0008).
- 5h Сохранение/загрузка общей кампании на хосте.
- Детект рассинхрона: периодические хэши ключевого состояния, лог расхождений.
- 5a: выяснить потерю крафтового предмета при save→load (корректность resume, research 0011). Таблица перевода ADR-0010 нужна только для дельт кампании; ссылки в бою — (type, StringId), рантайм-предметы по значению.
- **Gate G2** после 5c: синхронизация стабильна 1 час с 2 игроками — иначе пересмотр ADR-0010.

### Spike A1 — прототип синхронизации миссии (вариант A) · перед Phase 6 · 3–5 окон
- На Custom Battle: хост ведёт авторитетную SP-миссию; клиент открывает зеркальную миссию на той же сцене: ИИ выключен, собственный урон и логика миссии отключены, агенты-«куклы» ведутся снимками 20–30 Гц (позиция, направление, каналы действий, здоровье); один удалённый агент управляется вводом клиента.
- Сначала проверить по 1.4.8 нужные API: телепорт агентов, установка каналов действий, флаги движения/событий.
- **Gate A1** (уточнено 2026-10-25): 1 управляемый агент + 100 кукол, 10 мин без падений, задержка «ввод → видимый эффект на хосте» p95 < 150 мс на loopback, смерти включены, счётчики расхождений = 0, измеренная пропускная способность. Провал → пересмотр ADR-0006 (вернуться к B по условиям ADR).
- **A1b (1–2 окна, перед Phase 6)** — условия вердикта PASS WITH CONDITIONS: soak ≥ 10 мин на 100 агентах со смертями и счётчиками расхождений (живые, здоровье, ошибка позиции); ≥ 30 замеров «ввод → видимый эффект» (p95 < 150 мс); подавить/считать локальный урон клиента; воспроизвести или профилировать провал клиента на ~36 с; прогон с **эмуляцией потерь и задержки** (LiteNetLib SimulatePacketLoss/SimulateLatency) — второго ПК у владельца нет (2026-10-25); реальная сеть — только на плейтестах с тестерами (Phase 9/11).
- **Итог (2026-10-25, research 0012):** полевой бой 1+101, 12 мин, без падений, ack p50 ≈ 40 / p95 ≈ 62 мс, ≈ 70 КБ/с; смерти в soak отключены, loopback, один необъяснённый провал клиента на ~36 с. Осады: режим «марионетки» реализован, прогон `siege:n30` без падений (290 событий, 0 расхождений), но лестницы/метательные машины/анимации/снаряды не проверены — **по решению владельца (2026-10-25) осады вынесены за MVP — первый этап после MVP**. Вердикт architect-reviewer: **PASS WITH CONDITIONS**, ADR-0006 вариант A остаётся принятым (0012, «Review»).

### Phase 6 — Конвейер старта боя · 3–5 нед (+1–2 нед на зеркальный старт) · 6–10 окон
- Хост ловит столкновение, сериализует одновременные столкновения, ставит глобальную паузу.
- Рассылка приглашения; UI: сторона → список слотов (Gauntlet) → бронь → подтверждение/отказ.
- Слоты из участников `MapEvent` (обе стороны, PvP; осадные роли — после MVP); таймауты; отмена боя.
- Зеркальный старт миссии на клиентах: сцена, сид, список спавна по (type, StringId) (ADR-0010).
- **Готово, когда**: 4 игрока (или 1 + 3 фейка) проходят выбор и все попадают в миссию.

### Phase 7 — Синхронизация боя (вариант A) · 3–5 мес · 35–60 окон
- 7a один управляемый агент у удалённого игрока; 7b все агенты, бой, урон; 7c приказы/формации
  (лорд командует своим отрядом); 7d нокаут → повторный выбор/наблюдатель; 7e подкрепления, отступление;
  7f осады (орудия, лестницы, ворота) — **после MVP** (решение владельца 2026-10-25, ADR-0007);
  7g завершение боя. **Осады (7f) — первый этап после MVP; главный известный риск: объекты ведутся хостом по кадрам/анимациям и снаряды нужно реплицировать, одного состояния мало (0012, п. 15–18).**
- 7a ввод клиента → хост; 7b снимки всех агентов, атаки, снаряды, смерти, интерполяция позиций и дельта/сжатие снимков. Осады (7f) — после MVP (ADR-0007).
- **Gate G3** после 7b: задержка и стабильность приемлемы — иначе пересмотр ADR-0006.

### Phase 8 — Результаты боя → кампания · 2–3 нед · 4–6 окон
- Потери, раненые, пленные (в т.ч. лорды), добыча, опыт, отношения; снятие паузы; кейсы PvP.

### Phase 9 — Режимы хостинга · 3–5 нед · 6–10 окон
- Выделенный хост (по ADR-0011); Steam-приглашение: лобби, Rich Presence «присоединиться»,
  бэкенд транспорта №2 (Steam Networking). Документация для запуска сервера.

### Phase 10 — UX · 2–4 нед · 4–8 окон
- Список игроков, чат, индикаторы паузы/боя, уведомления, настройки (MCM — опционально), локализация RU/EN.

### Phase 11 — Надёжность · 1–2 мес · 10–20 окон
- Переподключение (через окно продолжения, SESSION_RESUME.md), отключение хоста/инициатора, краш-репорты, производительность, 10+ плейтестов
  по 4 игрока, совместимость с популярными модами (минимум — не падать).

### Phase 12 — Релиз · 1–2 нед · 2–3 окна
- Сборка, версия, Steam Workshop + Nexus, README/FAQ, лицензия MIT, changelog.

## 4. Рекомендуемый порядок «вертикальных срезов»

1. Мод грузится (P1). 2. Брони слотов в тестах (P3). 3. 4 фейка по сети (P4).
4. **Демо-бой на Custom Battle**: 2 реальных игрока, выбор стороны/слота, один управляемый агент (P6+7a без кампании).
5. Общая карта: 2 игрока двигаются, пауза (P5a–5c). 6. Бой из кампании → результат в кампанию (P6–8).
7. Остальная кампания, хостинг, полировка.

## 5. Риски

| Риск | Вероятн. | Влияние | Митигирование |

| Кампания не детерминирована, рассинхрон | высокая | критич. | хост-авторитет, хэши состояния, Gate G2 |
| Рассинхрон/трудоёмкость собственной репликации агентов (вариант A) | высокая | критич. | Spike A1 + Gate A1 до Phase 6, Gate G3; условия возврата к B в ADR-0006 |
